# Connect the actual Switch service

1. Install the official Windows Switch Console from https://docs.switchagents.ai/switch-rooms/getting-started/install-switch-console . Run its supported server setup; connect Mattermost using the official bridge setup. Switch is intentionally not bundled as an invented image.
2. Copy the **server/bridge** address, not a separately hosted Gateway address. `GET <address>/health` must return 200. In Docker use `host.docker.internal` to reach a host service; do not use `localhost` inside a container for host services.
3. In the Gateway **API Keys** page, create a key of type **registration** owned by the intended human. Add server URL and registration key in SwitchOps **Integrations → Switch Rooms → Configure**.
4. In **AI Agents**, register each of the six agents exactly once. Existing names return 409 and are never overwritten. Keys are stored encrypted. Registration is committed before addressing setup so a follow-up error cannot discard the one-time key.
5. Set `addressing: owner_and_owner_agents` on all six identities. SwitchOps attempts this via the discovered `update_agent_detail` operation. In Switch Console grant any additional verified human participants access through custom rules. Do not use `anyone` casually.
6. In Switch Console **Templates → Import template**, paste `switch/templates/business-workspace.yaml`. Select your genuine Mattermost bridge and **Create all**. All named custom agents must already exist. This uses format version 1, supported by the published template reference; verify import against your installed release.
7. Read the exact opaque participant IDs and room IDs from Switch room context/participant information. In SwitchOps **AI Agents → Manage**, map each participant ID and the operations-hub room ID. Do not derive participant IDs from names. Each participant ID is compared exactly on every received handoff.
8. In **Switch Rooms**, map operations-hub and its actual Mattermost conversation URL. Map the other rooms for navigation if desired. In **Settings**, set the default operations-hub room ID.
9. Map verified human Switch participant IDs to application user UUIDs in Settings. User UUIDs are available in `/api/v1/users`. Room requests require both this mapping and a real membership; viewers cannot start work. Dashboard approval is the supported authorization path; chat approvals are not implemented.
10. Configure a real model in Integrations, test availability, then start `scripts/windows/start.ps1 agents` (or the Docker agents service). The six agents must report real heartbeats. All six share operations-hub for the flagship workflow; the smaller topical rooms retain their purpose and are not automatic cross-room workflow routers.

SwitchOps uses the released documentation for registration, WebSocket events, cursor/generation fencing, heartbeat pongs, discovered HTTP operations and `/agents/{id}/message`. No undocumented admin API is used. Live import and handoffs remain unverified until an installed server and credentials are supplied.
